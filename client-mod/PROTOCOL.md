# KunxunAuth Device 线协议 v1

本文面向 **服务端插件实现者**。读完你应该能不看 Java 代码，独立用任意语言/任意服务端平台
（Paper / Spigot / Fabric 服务端 / 代理端）实现这套「设备免密登录」。

---

## 1. 这套协议解决什么问题

玩家的账号里可以绑定若干台「设备」。每台设备在本地持有一对 Ed25519 密钥，
私钥永不出机器。玩家进服时，服务端发一个**每次都不一样的随机挑战**，客户端用私钥签名回传，
服务端用之前登记的公钥验签：

- 验签通过 → 证明「发来应答的这台机器，确实持有当初绑定过的私钥」→ 可以直接放行，不用输密码。
- 验签失败 / 超时 / 客户端根本没装模组 → 退回正常的密码（或验证码）登录流程。

协议里不出现密码，也不出现任何长期有效的凭据。每次登录都是一次新的随机挑战。
**重放一次旧应答是没用的**，因为 nonce 变了。

## 2. 传输层

| 项目 | 值 |
| --- | --- |
| 通道命名空间 (namespace) | `kunxunauth` |
| 通道路径 (path) | `device` |
| 完整标识 | `kunxunauth:device` |
| 负载类型 | **UTF-8 字符串**（不是 NBT、不是 JSON、不是二进制结构） |
| 方向 | 双向：服务端 → 客户端 一个包，客户端 → 服务端 一个包 |

负载内容本身是一个用 `|`（U+007C，竖线）分隔的**纯文本**字符串。它被当作一个整体，
塞进各加载器的自定义负载（custom payload / packet）里原样传输，客户端只是把它读出来再写回去。
之所以选纯文本而不是 NBT/JSON：字符串在任何平台、任何 MC 版本上都不需要额外的编解码器，
服务端插件可以用 `String.split("\\|", -1)` 三行代码解析完。

### 2.1 负载标识（区分两个方向的包）

同一个通道下，用负载标识区分两个包：

| 标识 | 方向 | 说明 |
| --- | --- | --- |
| `challenge` | 服务端 → 客户端 | 挑战 |
| `response` | 客户端 → 服务端 | 应答 |

> 实现方式随加载器不同：
> - **Fabric**：用两个不同的 `CustomPacketPayload.Type`，id 分别是
>   `Identifier.fromNamespaceAndPath("kunxunauth", "challenge")` 和 `...("kunxunauth", "response")`。
> - **NeoForge / Forge**：注册在 `kunxunauth:device` 这一个通道/ID 上，用包体第一个字段之外的一个
>   显式前缀区分；见第 5 节的「单通道变体」。
>
> 两种做法在**线格式层面完全等价**：你收到的字符串长什么样、你要回什么字符串，是一样的。

### 2.2 发送时机：**配置阶段（configuration phase）**

这一点最容易踩坑。设备挑战在玩家**还没进入世界**的配置阶段就要发出去，
原因是把它放在登录流程里，玩家会先看到「正在登录…」的空场景界面。
Minecraft 1.20.2 之后，客户端与服务器之间有三段状态：

```
handshake → (login) → configuration → play
```

配置阶段是**唯一**一个既已经完成了身份握手、又还没进入世界、而且允许双向自定义负载的阶段。
各加载器的配置阶段网络 API 名称见 README。

> 如果你的服务端是纯 Paper/Spigot 插件（Bukkit API 没有配置阶段的概念），
> 那就退到 **play 阶段**发挑战，把「免密」当成进入世界后的一次性校验：
> 校验通过就解锁，超时未通过就让玩家落到密码登录。协议格式完全不用改。

## 3. 线格式

所有字段都是 UTF-8 文本。**第一个字段永远是协议版本号**，这样以后改格式时
老客户端可以「优雅退出」而不是「验签失败」——后者会让玩家以为自己的设备坏了。

### 3.1 服务端 → 客户端：`challenge`

```
1|nonce|serverId|playerName
```

| 序号 | 字段 | 说明 |
| --- | --- | --- |
| 0 | `version` | 协议版本。**挑战侧恒为 `1`**：这个字段从第一版起就没变过，把它提到 2 只会让所有老客户端静默不回包，等于用一次服务端升级把玩家的免密整体关掉。不等于自己支持的版本就**不要签发应答**，直接忽略该包。 |
| 1 | `nonce` | 服务器生成的随机数，**Base64url、无填充**（见 §4）。建议 ≥ 16 字节熵。 |
| 2 | `serverId` | 服务器标识。用来把签名绑死到某一台服务器，防止 A 服的挑战被拿到 B 服重放。建议全网唯一且稳定。 |
| 3 | `playerName` | 本次要验证的玩家名。**必须原样参与签名**（见 §5.2）。 |

字段里不允许出现 `|`。客户端/服务端在编码时都会把字段内的 `|` 剔除，
防止有人把玩家名写成 `a|b` 来让字段错位。

### 3.2 客户端 → 服务端：`response`

```text
2|publicKey|signature|deviceName|fingerprint     （v2，1.1.0+ 客户端）
1|publicKey|signature|deviceName                 （v1，1.0.0 客户端）
```

| 序号 | 字段 | 说明 |
| --- | --- | --- |
| 0 | `version` | `2` = 带设备指纹；`1` = 不带。**字段数必须与版本号自洽**：v1 只能有 4 段，v2 只能有 5 段。服务端两者都要接受，这样老模组连到新插件照样能免密，只是指纹那一栏是空的。 |
| 1 | `publicKey` | 设备公钥，**X.509 DER 编码后再 Base64url（无填充）**。Ed25519 公钥 DER 固定 44 字节，Base64url 后固定 59 个字符。 |
| 2 | `signature` | **Ed25519 签名，64 字节，Base64url（无填充）**。 |
| 3 | `deviceName` | 设备自报的名字，给人看的（例如 `DESKTOP-ABC-4821`）。**不要用它做任何安全决策**，它只是让玩家在「已绑定设备」列表里认出哪台是哪台。 |
| 4 | `fingerprint` | 硬件指纹摘要（v2 才有）。客户端把 CPU / 主板 / 系统盘 / 机器 ID 拼起来做 SHA-256，取 Base64url 前 32 位。**它不是凭据**：公钥验签才是放行依据，指纹只用来回答「这台机器还是不是当初绑定那台」。详见 §5.6。 |

### 3.3 签名的内容

客户端签的不是整个包，而是下面这个拼接串的 UTF-8 字节：

```
nonce + "|" + serverId + "|" + playerName
```

注意**没有**协议版本号前缀。`nonce` 是 Base64url 字符串本身（不是解码后的字节），
`serverId` / `playerName` 是挑战里收到的原文。

服务端验签时用**完全相同的拼接规则**重建这段字节，用 `publicKey` 验 `signature`。

> 具体到密码学 API：
> - Java：`Signature.getInstance("Ed25519")`
> - 公钥：`KeyFactory.getInstance("Ed25519").generatePublic(new X509EncodedKeySpec(der))`
> - Python：`cryptography.hazmat.primitives.asymmetric.ed25519.Ed25519PublicKey.from_public_bytes(raw32)`
>   注意 Python 要的是 **32 字节裸公钥**，而 Base64 里是 44 字节 X.509 DER。
>   裸公钥在 DER 里的位置是**最后 32 字节**（前 12 字节是 `302a300506032b6570032100` 这个固定头）。

## 4. Base64 的确切用法

协议里的 Base64 一律是 **Base64url、去掉 `=` 填充**（RFC 4648 §5，URL-safe alphabet `-` `_`）。

这是为了避免三个经典的跨平台坑：

1. 标准 Base64 的 `+` `/` 在 URL、JSON、YAML 里都要转义；
2. 填充 `=` 在不同实现里有的补有的不补，字符串比较会莫名失败；
3. 线上历史上有过把 `+` 当空格处理导致验签失败的案例。

解码时要先把 `=` 补回去（长度补到 4 的倍数）。参考实现见
`common/src/main/java/top/kunxun/device/DeviceKeyStore.java` 的 `pad()`。

## 5. 安全考量

这一节是**必须读**的部分。协议本身很短，安全性几乎全部取决于服务端怎么用它。

### 5.1 nonce 防重放（最重要）

- `nonce` 必须是**密码学安全的随机数**（`SecureRandom` / `/dev/urandom`），
  不要用 `Math.random()`、不要用时间戳、不要自增。
- 建议至少 **16 字节（128 bit）** 熵。
- nonce 必须**一次性**：验证成功后立刻作废；验证失败也必须作废。
- nonce 建议**绑定上下文**：`nonce → {playerName, serverId, 签发时间}`，验证时逐项比对。
  - 攻击者如果能把 A 玩家收到的 challenge 原样转发给 B 玩家，而 B 玩家的客户端照签，
    那么没有上下文绑定的话 B 就成了 A。绑定 `playerName` **在服务端**这一侧
    能堵住这种「挑战转发」。
- nonce 要有**过期时间**，建议 30–120 秒。过期的 nonce 直接拒绝，不要让它在内存里烂掉。

**为什么这很重要**：`response` 里的 `signature` 对同一组 `(nonce, serverId, playerName)`
是**恒定**的（Ed25519 是确定性签名算法）。如果不换 nonce，攻击者只要在网络上抓到一次
`response`，就能永久重放它，等同于偷到设备。

### 5.2 签名覆盖 playerName 防冒名

签名原文里包含 `playerName`，意思是：
「这台设备的私钥持有者，明确声明自己要登录的是 `<playerName>` 这个账号」。

于是即使攻击者拿到了别人设备的 `response` 包，他也只能用它登录**那个玩家的账号**
（而且还要面对 nonce 校验），没法把它改成自己的名字。

反过来，**服务端必须做的一件事**：验签时用「当前这个连接的真实玩家名」重建签名原文，
而不是用 `response` 里带的任何字段。`response` 里根本没有 playerName 字段，
就是为了让服务端没得选——它只能用自己的上下文，攻击者无从注入。

### 5.3 私钥文件的保管方式

客户端的私钥存在游戏目录下的 `kunxun-device/<账号>-<摘要>.properties`，
**一个账号一份**。为什么要按账号分而不是全机一份：服务端用「公钥」识别设备，
而公钥在设备表上是唯一的；如果一台机器上所有账号共用一把密钥，第二个账号拿去绑定
只会撞上唯一约束，于是那个账号永远免不了密。这是一条很容易被忽略、上线后才发现的问题。

**这个文件仍然是凭据**，但它落盘时是加密的：密钥由本机硬件指纹（CPU / 主板 /
系统盘 / 机器 ID 的摘要）经 PBKDF2 派生，密文用 AES-256-GCM 认证加密
（账号名进 AAD）。于是把文件复制到另一台机器上，**解不开、拿不到私钥**，
客户端会生成一把新密钥、要求重新绑定。这就是「密钥跟设备绑定」的实现方式，
详见 §5.6。

由此推出服务端必须承担的责任：

1. **设备数上限**。每个账号允许绑定的设备数要有上限（建议 3–5 台）。
   没有上限的话，账号被盗后你连「哪些是设备」都说不清。
2. **必须提供吊销能力**。至少要有：
   - 玩家自助的「查看已绑定设备列表 + 删除某台设备」；
   - 封禁/改密时**一键吊销全部设备**（这是账号被盗后的第一处置动作）。
   吊销 = 从服务端把对应 `publicKey` 删除。私钥还在玩家机器上，但服务端不认了。
3. **公钥是主键**。识别一台设备用 `publicKey`，不用 `deviceName`，也不要用指纹。
   `deviceName` 是玩家可以随便改的自由文本，同名设备是常态；指纹是公开信息，
   可以被伪造（见 §5.6）。
4. **公钥不可冒充注册**。加设备（绑定）这一步**必须先经过一次正常的密码/验证码登录**。
   如果绑定接口不鉴权，攻击者可以把**自己的**设备悄悄绑到别人账号上，形成长期后门。
5. **换硬件要能自愈**。指纹不一致时正确做法是「作废这条绑定，让玩家密码登录后重新绑」，
   而不是把玩家挡在门外。作废这一步不能省：留着旧记录会让玩家重新绑定时撞上
   「这台设备已经绑过了」，于是永远卡在输密码上。
6. **提醒玩家**。客户端在生成密钥时会在日志里提示「这个文件是凭据，不要外传、不要提交到仓库」。

### 5.4 服务端不应做的事

- **不要信任 `deviceName`**：只做展示，不要参与任何判定或存储为主键。
- **不要在没有 nonce 校验的情况下直接接受 `response`**：那等于把设备公钥当成万能钥匙。
- **不要因为协议异常踢人**：收到畸形负载、未知版本、验签失败，正确做法是
  **记一条日志然后忽略这个包**，让玩家走密码登录。
  协议异常是攻击者的日常操作，不应该变成「把正常玩家挡在门外」的手段。

### 5.5 已知的、这套协议**不**解决的问题

诚实地列出来，避免误用：

| 不解决 | 说明 | 缓解方式 |
| --- | --- | --- |
| 私钥文件被复制到另一台机器 | 文件是用本机硬件指纹派生的密钥加密的，换机器解不开（§5.6） | 客户端自动换新密钥 + 服务端设备数上限 + 吊销 + 异常登录告警 |
| 同一台机器上伪造硬件指纹 | 指纹字段都是本机可读的公开信息，一个刻意伪造指纹的程序仍能解出私钥 | 无（需要 TPM 之类的硬件密钥库）。真正的凭据始终是私钥，指纹只是第二道判断 |
| 客户端被中间人篡改 | 模组跑在玩家机器上，玩家可以拿改过的客户端签任何东西 | 签名只证明「私钥持有者」，不证明「客户端未被修改」。**真正确认玩家身份仍然需要一次密码**（首次绑定） |
| 网络层窃听 | 挑战/应答是明文的 | MC 本身走加密连接；此外签名是一次性的，抓包价值有限 |
| 服务器伪装 | 客户端无法确认对面是不是真服务器 | `serverId` 参与签名能减轻「挑战被转发到另一台服务器」的重放，但不能防钓鱼式伪服 |
| 量子计算 | Ed25519 不是后量子算法 | 版本号机制允许以后平滑换算法 |

### 5.6 设备指纹：它是干什么的，以及它**不是**什么

v2 应答多出来的 `fingerprint` 字段，是客户端对本机硬件信息的摘要：

```text
CPU 序列号 / 主板序列号 / 主板型号 / 系统盘序列号 / 机器唯一 ID
        ↓ 拼起来做 SHA-256，取 Base64url 前 32 位
fingerprint
```

**它是干什么的**：

1. 客户端用它（加盐、PBKDF2 之后）派生密钥，加密自己那份私钥文件（§5.3）；
2. 服务端把它存进设备表，用来回答「这次来的是不是当初绑定那台机器」。

**服务端拿到它该怎么用**：只当作**辅助判定 + 证据**。

- 建议做成三档开关：不校验 / 只记录告警 / 强制校验（不一致就作废该绑定，让玩家重新绑）。
- 强制校验那一档也必须**可自愈**：作废绑定 → 玩家密码登录 → 重新绑定。
  绝不能变成「这台设备永远进不去」。
- **不要**把它当主键，**不要**在没有验签的情况下因为指纹一致就放行。

**它不是**：不是凭据，不是硬件保险箱，不是 TPM。理由很直白 —— 这些字段
本机上任何程序都读得到，也能被伪造。它的价值在于把「把密钥文件拷到别的机器用」
这条最省事的攻击路径堵死，并且让「换机器」这件事在服务端留下痕迹。

## 6. 服务端实现清单

按顺序做，缺一不可：

1. 在**配置阶段**（或 play 阶段，见 §2.2）注册 `kunxunauth:device` 通道的双向负载。
2. 玩家连接时生成 `nonce`（≥16 字节 SecureRandom → Base64url 无填充），
   连同 `serverId`、`playerName` 存进一个带过期时间的表。
3. 发送 `1|nonce|serverId|playerName`。
4. 收到 `response` 后：
   a. 按 `|` 拆开，**先看字段数与版本号是否自洽**：`1` 配 4 段、`2` 配 5 段，其余一律丢弃并记日志；
   b. 第一段是 `1` 或 `2`，其余值丢弃并记日志；
   c. 用你**自己记录的** `playerName`、`serverId`、`nonce` 重建签名原文；
   d. 查库：该 `publicKey` 是否属于该玩家、是否已被吊销、该玩家设备数是否超限；
   e. 用 `publicKey` 验 `signature`；
   f. 成功后立刻**销毁 nonce**（无论成败）。
5. 验签通过后再看指纹（v2 才有）：
   - 库里没有存过指纹 → 顺势补记，本次放行；
   - 指纹一致 → 放行；
   - 指纹不一致 → 按配置决定「只告警」还是「作废这条绑定」（作废后玩家密码登录可重新绑定）。
   **无论哪一档，都不能因为指纹不一致就把人踢下线**，最多是不给免密。
6. 验签通过 → 放行；任何一步失败 → 记日志、忽略该包，回落到密码登录。
7. 提供「列出设备 / 吊销设备 / 改密时全量吊销」的管理接口。
8. 发 challenge 之前记得先看这条连接上有没有在等应答的挑战，别重复发；
   连接断掉时把对应的 `nonce` 一起销毁，否则它会在内存里留到过期。

### 6.1 客户端**一定**会发的东西

服务端可以依赖以下事实（这些类在三个加载器里是同一份字节码）：

- 客户端只在收到 **协议版本 = 1** 的 `challenge` 时才回 `response`；版本不符时**静默忽略**。
- 客户端回复的 `publicKey` 对**同一个账号同一台机器**是稳定的，**每次登录都一样**。
- **不同账号不共用密钥**：同一台电脑上一个正版号加一个离线小号，上报的是两把不同的
  `publicKey`，各自绑定。所以服务端不要假设「一台机器 = 一把公钥」。
- 客户端**不会**因为收不到 challenge 而报错；它完全被动。
- 客户端的 `nonce` 字段处理是**字符串透传**：它不解析、不校验 nonce 的格式，
  拿到什么就把它原样拼进签名原文。所以 nonce 里除了 `|` 之外用什么字符集都可以。
- 1.1.0+ 客户端的应答是 **5 段的 v2**（带指纹）；1.0.0 客户端是 **4 段的 v1**。
  两版客户端都可能出现在同一台服务器上，所以两种都要认。

---

## 7. 版本演进

**挑战侧**的 `version` 一直是 `1`，而且短期内不要动它 —— 客户端只认「等于自己支持的
那一个」，改它等于把所有老客户端静默关在免密之外。

**应答侧**目前是 `2`（多了 `fingerprint`）。服务端必须同时接受 `1` 和 `2`，
判断依据是「字段数与版本号自洽」。这条规则让协议可以一路加字段而不用逼所有人一起升级。

设想中的演进：

- 要加字段 → 应答版本号 +1，**保留对旧版本的解析**，服务端按版本分派处理。
- 要换算法（例如换到后量子签名）→ 挑战版本号也要动，但那意味着老客户端会静默不回包，
  必须提前把「升级客户端」这件事通过公告之类的方式推给玩家，不能靠协议自己兜。
- 客户端遇到不认识的挑战版本会**安静地不回包**，服务端看到的就是「这个玩家没有设备凭据」，
  自然回落到密码登录。这是有意设计的降级路径：**协议升级不应该让任何玩家卡在门外**。
